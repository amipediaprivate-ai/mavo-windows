# 本地索引数据库备份与恢复

## 数据位置

Caevir 的索引数据库是应用数据目录下的 `caevir-index.sqlite3`。本文用 `<app-data>` 表示 Tauri 在当前 Windows 用户下解析出的 Caevir 应用数据目录；不要把它与安装目录或素材目录混淆。

- 主数据库：`<app-data>/caevir-index.sqlite3`
- 自动备份：`<app-data>/database-backups/`
- 损坏或迁移失败现场：`<app-data>/database-quarantine/<时间戳>-<原因>/`
- 无法自动恢复时的保护标记：`<app-data>/caevir-index.recovery-required`

备份和现场目录都位于应用数据目录内，不会写入素材库。测试使用系统临时目录中的独立工作区，不读取或修改真实用户 AppData。

## 自动备份与保留策略

数据库使用 WAL 模式。自动备份通过 SQLite Online Backup API 从已打开的连接生成一致性快照，已提交但仍在 `-wal` 中的内容会进入备份；实现不会在数据库打开时只复制主文件。

启动时，在 watcher、扫描器和其他后台任务开始之前执行数据库生命周期流程：

1. 清理上次崩溃遗留的未完成备份临时文件。
2. 对现有数据库执行 `PRAGMA integrity_check`、外键检查和架构版本检查。
3. 有迁移时先生成并验证 `pre-migration` 快照；快照写入临时文件，完整性验证及磁盘同步成功后才原子改名为正式备份。
4. 执行迁移，记录 `PRAGMA user_version`，再验证完整性、外键和必需表/字段。
5. 启动验证成功后生成一个 `startup` 快照。

自动备份按文件名时间戳倒序滚动，只保留最近 **5** 个经过验证的 `.sqlite3` 快照。新的迁移必须同步递增 Rust 代码中的 `CURRENT_SCHEMA_VERSION`，否则生命周期管理器不会把该变更识别为迁移。

## 自动恢复

- 当前数据库损坏或当前版本架构不完整时，Caevir 从新到旧检查备份；损坏、不可读或来自不受支持的更高架构版本的备份会被跳过。
- 找到可恢复备份后，当前主文件及其 `-wal`、`-shm` 会先整体移动到 `database-quarantine`。备份先复制到同目录临时文件，经过再次完整性检查和磁盘同步后，再原子改名为主数据库。
- 恢复后的旧架构数据库仍需正常通过迁移及迁移后验证。迁移失败时，失败现场会被隔离，迁移前快照会恢复到主路径，应用停止启动并返回明确错误。
- 如果主数据库缺失但备份目录仍存在（例如恢复期间崩溃），启动流程会优先恢复最近的有效备份，不会创建空库。
- 如果没有有效备份或回滚本身失败，Caevir 会保留现场、写入保护标记并停止启动；不会静默删除数据或用空库覆盖。

进程内的数据库生命周期由全局互斥锁串行化，避免并发命令重复备份或恢复。运行期普通命令只打开数据库连接，不会替换数据库文件；恢复仅发生在安全的启动阶段。

## 人工恢复边界

Caevir 当前没有“重置数据库”或从任意文件导入数据库的界面。自动恢复失败时：

1. 完全退出 Caevir，并确认没有 `caevir.exe` 进程。
2. 先复制保存整个 `<app-data>`，尤其是主数据库、`-wal`、`-shm`、`database-backups` 与 `database-quarantine`；不要直接删除现场。
3. 可将一个已确认有效的自动备份复制到应用数据目录，命名为 `caevir-index.sqlite3`。备份文件本身是完整 SQLite 快照，不需要同时复制同名 WAL/SHM。
4. 只有在主数据库已放回且后续启动验证成功后，才可移走 `caevir-index.recovery-required`。应用也会在成功验证后自动清除此标记。

删除主数据库并不等同于重置：只要备份仍在，Caevir 会尝试恢复。确需放弃全部索引数据时，应先离线归档整个应用数据目录，再由维护人员明确移走主数据库、备份和保护标记；Caevir 不会替用户自动执行这一不可逆操作。
